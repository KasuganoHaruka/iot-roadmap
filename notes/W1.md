## 一、RS-232 与 RS-485 的根本差异

| | RS-232 | RS-485 |
|---|---|---|
| 信号方式 | **单端**：一根信号线对地 | **差分**：A/B 两线的**电压差** |
| 逻辑判定 | 相对 GND 的绝对电平（±3~15V） | `V(A) − V(B)`，差值 > +200mV 为 1，< −200mV 为 0 |
| 抗干扰 | 差 —— 干扰直接叠在信号上 | **强** —— 干扰同时叠在 A 和 B 上，相减抵消（共模抑制） |
| 距离 | ~15 米 | **1200 米 @ 100kbps** |
| 拓扑 | 点对点 | 多点，一条总线最多 32 个标准负载 |

**要能讲出来的那句话**：差分不是"用两根线传一个信号"，而是**只看两根线的差值**。外界干扰是共模的（等量地加在 A 和 B 上），相减就没了。这是 485 能跑 1200 米而 232 跑 15 米就完蛋的全部原因。

> 经验公式：**速率 × 距离 ≈ 常数**。9600bps 能跑 1200 米，115200bps 就只剩百米级。现场跑不通先把波特率降下来试，这是最快的二分法。
>
> 电气细节的权威出处是 TI 的应用手册
> [*The RS-485 Design Guide* (SLLA272D)](https://www.ti.com/lit/an/slla272d/slla272d.pdf) ——
> 20 页，讲透了终端匹配、共模范围、失效保护偏置。本周只需读前两节。

### A/B 极性

接反了不会烧，但**收不到数据**（或者收到一堆帧错误）。不同厂家丝印还不统一：有的写 A/B，有的写 D+/D−，有的写 485+/485−。一般 A = D+ = 485+。

**排查手法**：接反和没接线的现象很像。两根线对调一次再试，比翻手册快。

## 二、终端电阻：只装两端，装错了就随机丢包

信号在传输线末端会**反射**，反射波和原信号叠加会把电平打乱。终端电阻的作用是让线路阻抗匹配，把能量吸收掉而不是弹回来。

```
        [主站]───┬─────────┬─────────┬───[从站3]
        120Ω     从站1     从站2         120Ω
        ↑                                  ↑
     物理两端各一个，中间的一个都不能装
```

**为什么中间不能装**：并联电阻会把总阻抗拉低。三个 120Ω 并联 = 40Ω，驱动器带不动，信号幅度不够，表现就是**随机丢包**——时好时坏，最难查的那种故障。

**W1 必做的对比实验**：故意不装终端电阻，用长线跑，记录误码率；再装上，再记录。有示波器最好（能直接看到反射的振铃），没有就看通信成功率。**这个实验做过，面试时说出来的分量完全不一样。**

### 屏蔽层：单端接地

屏蔽层两端都接地，会形成**地环流** —— 两端地电位不等，电流从屏蔽层上流过，反而把干扰引进来。所以**只接一端**（通常接主站侧）。

### 共地问题

差分只是抗共模干扰，不是不要地。485 收发器有**共模电压范围**（典型 −7V ~ +12V）。如果两台设备的地电位差超出这个范围，收发器根本判不出电平。长距离或跨配电箱时，要么加**隔离型**收发器，要么单独拉一根信号地。

> 你的 P0 清单里那句"USB 转 485 **必须带隔离**"，理由就在这里。

### 拓扑必须是手拉手

菊花链，不能星型、不能长支线。星型接线等于制造了多个反射点，终端电阻也无从装起。现场最常见的三个错误就是：**星型接线、终端电阻装了三个、屏蔽层两端接地。**

## 三、C# SerialPort 的坑

> 参考：[`SerialPort` 类文档](https://learn.microsoft.com/dotnet/api/system.io.ports.serialport)
> ——尤其是 `ReadTimeout`、`DataReceived`、`BytesToRead` 三个成员的备注段。

### 坑 1：`DataReceived` 不等于"一帧到了"

串口是**字节流**，没有消息边界。`DataReceived` 事件在驱动缓冲区有数据时触发，**触发次数和帧数没有任何关系**。一帧 8 字节可能触发 1 次，也可能触发 5 次（分包）；两帧也可能挤在一次触发里（粘包）。

**W1 必做实验**：写个最小收发程序，让对端连续快速发几帧，数一数 `DataReceived` 触发了几次。亲眼看到"次数对不上"，这个坑就永远记住了。

### 坑 2：`Read` 不保证读满

```csharp
// 错的：以为 Read 会读满 count 个字节
port.Read(buf, 0, 8);

// 对的：循环读到够为止，并且带超时
static int ReadExactly(SerialPort port, byte[] buf, int count, int timeoutMs)
{
    var got = 0;
    var deadline = Environment.TickCount64 + timeoutMs;
    while (got < count)
    {
        var left = (int)(deadline - Environment.TickCount64);
        if (left <= 0) throw new TimeoutException($"只读到 {got}/{count} 字节");
        port.ReadTimeout = left;
        got += port.Read(buf, got, count - got);   // 可能一次只给你 1 字节
    }
    return got;
}
```

`ReadTimeout` 只管**单次** `Read` 等多久，不是整帧的超时。整帧超时要自己用截止时间算。

### 坑 3：`BytesToRead` 是快照

读它的下一刻缓冲区就可能变了。**不要**用 `if (BytesToRead >= 8) Read(...)` 这种写法当分帧逻辑。

### 分帧器：定长 + 超时

Modbus RTU 的正统分帧靠**帧间静默 3.5 个字符时间**，但在 Windows/Linux 的用户态拿不到那么精确的时序。工程上的做法是：

1. **已知长度**：先读固定的头部（RTU 响应的第 3 字节就是字节计数），算出总长，再 `ReadExactly` 剩下的；
2. **超时兜底**：整帧超时到了还没读满，丢弃并重试；
3. **收到脏数据就清缓冲**：`DiscardInBuffer()`，避免半帧残留污染下一次。

W1 的任务里那条"写一个定长 + 超时的串口分帧器，单元测试覆盖分包/粘包/超时三种情况"，就是把上面这套写成可测的代码。**测试要能构造出分包**——把一帧拆成两次喂进去，断言分帧器仍然只吐出一帧。

## 四、TCP 也一样：粘包 / 半包

很多人以为"TCP 可靠所以不会丢" —— TCP 保证的是**字节流有序不丢**，从来没保证过消息边界。`NetworkStream.Read` 和串口的 `Read` 是同一个坑。

```csharp
static async Task ReadExactlyAsync(Stream s, Memory<byte> buf, CancellationToken ct)
{
    var got = 0;
    while (got < buf.Length)
    {
        var n = await s.ReadAsync(buf[got..], ct);
        if (n == 0) throw new EndOfStreamException("对端关闭了连接");
        got += n;
    }
}
```

> .NET 7 之后有内置的
> [`Stream.ReadExactlyAsync`](https://learn.microsoft.com/dotnet/api/system.io.stream.readexactlyasync)，
> 但**自己写一遍**再去用它。面试问"粘包怎么处理"，你要能顺手写出这十行，而不是答"调个库"。

Modbus TCP 的边界靠 MBAP 头里的**长度字段**：先读 6 字节头，取出长度，再读那么多。下周 W2 会逐字节拆这个头。
