## 一、自己起一个 OPC UA Server

W11 是当客户端去连别人，这周反过来：把 Modbus 采到的数据**建成 OPC UA 节点暴露出去**。

**为什么值得做**：现场很常见的架构是"老设备只有 Modbus → 网关转成 OPC UA → MES/SCADA 统一接入"。你做的就是这个网关。而且——**能自己实现服务端，说明你真的理解了地址空间**，不只是会调客户端 API。

```csharp
public sealed class IiotNodeManager : CustomNodeManager2
{
    public override void CreateAddressSpace(IDictionary<NodeId, IList<IReference>> externalRefs)
    {
        var root = CreateFolder(null, "Plant", "工厂");
        foreach (var line in _config.Lines)
        {
            var lineNode = CreateFolder(root, $"Plant.{line.Id}", line.Name);
            foreach (var dev in line.Devices)
            {
                var devNode = CreateFolder(lineNode, $"Plant.{line.Id}.{dev.Id}", dev.Name);
                foreach (var tag in dev.Tags)
                    CreateVariable(devNode, $"Plant.{line.Id}.{dev.Id}.{tag.Name}",
                                   tag.Name, DataTypeIds.Double, ValueRanks.Scalar);
            }
        }
    }
}
```

## 二、信息模型：层级，不是平铺

**这是本周最容易做错、也最容易讲出价值的一点。**

```
✗ 平铺（等于把 OPC UA 当 Modbus 用，白瞎了）
  Tag0001, Tag0002, Tag0003, ... Tag2000

✓ 层级
  Plant
   └── Line1
        ├── Motor3
        │    ├── Speed   (Double, EURange 0..3000, EngineeringUnits "rpm")
        │    ├── Current (Double)
        │    └── Status  (Int32)
        └── Pump1
             └── ...
```

平铺的地址空间让客户端**无法自我发现**——它不知道 Tag0042 属于哪台设备。层级模型让 SCADA 连上来就能自己长出一棵设备树，不需要人工对点表。

**加上属性会更专业**：

- `EngineeringUnits`（工程单位："℃"、"rpm"）
- `EURange`（量程上下限——**Percent Deadband 依赖它**）
- `Description`（中文描述）

**验收**：用 UaExpert 连自己的 Server，能浏览出这棵树、能订阅、数值在动。这就是 M3 闸门的第一条。

## 三、统一驱动抽象（本周的架构核心）

三个协议，一个接口：

```csharp
public interface IDeviceDriver
{
    string Id { get; }
    Task ConnectAsync(CancellationToken ct = default);
    Task DisconnectAsync(CancellationToken ct = default);
    Task<IReadOnlyList<TagValue>> ReadAsync(IReadOnlyList<TagDefinition> tags, CancellationToken ct = default);
    Task WriteAsync(TagDefinition tag, object value, CancellationToken ct = default);
    DriverStatistics Statistics { get; }
}
```

```
        采集调度器（W4 写的）
               │  只认 IDeviceDriver
    ┌──────────┼──────────┐
ModbusDriver  S7Driver  OpcUaDriver
```

**抽象的边界在哪**（这是能不能讲清楚的关键）：

- **共性**：连接生命周期、批量读、单点写、质量统计、超时重试 → **进接口**
- **个性**：地址格式、字序、DB 块对齐、NodeId 命名空间 → **进各自的配置，不进接口**

> **不要试图设计一个能表达所有协议地址的通用结构。** 地址就存字符串（`"4x0001"` / `"DB1.DBD4"` / `"ns=2;s=Line1.Motor3.Speed"`），由各驱动自己解析。这是**刻意的不抽象**，理由是三种协议的地址模型根本不同构，硬统一只会造出一个谁都不好用的怪物。
>
> 面试时主动讲这个取舍，比讲"我做了抽象"有价值得多。

## 四、点表驱动：加设备不改代码

```json
{
  "devices": [
    {
      "id": "line1-meter1",
      "driver": "modbus-rtu",
      "connection": { "port": "/dev/ttyModbus0", "baudRate": 9600, "unitId": 1 },
      "pollIntervalMs": 1000,
      "tags": [
        { "name": "Temperature", "address": "4x0001", "type": "Float32",
          "wordOrder": "CDAB", "scale": 0.1, "unit": "°C",
          "alarmHigh": 80, "alarmLow": -10 }
      ]
    },
    {
      "id": "line1-plc",
      "driver": "s7",
      "connection": { "host": "192.168.1.10", "rack": 0, "slot": 1 },
      "tags": [ { "name": "Count", "address": "DB1.DBW2", "type": "Int16" } ]
    }
  ]
}
```

**每个字段都是踩过的坑变来的**：`wordOrder` 来自 W3，`scale` 来自"仪表返回 255 表示 25.5℃"，`unit` 给 OPC UA 的 EngineeringUnits 用，`alarmHigh/Low` 给 W18 的告警引擎用。

**这份配置的存在本身就是产品化的证据**：加一台设备是改配置，不是改代码、不是重新编译、不是重新部署。

## 五、OPC UA vs MQTT：为什么现场常见"UA 采 → MQTT 上云"（Q24）

**这是 M3 闸门的第三条，必须能口述。**

| | OPC UA | MQTT |
|---|---|---|
| 定位 | **设备互操作**——统一语义 | **消息传输**——高效搬运 |
| 模型 | 有类型的地址空间，自描述 | 主题 + 不透明载荷 |
| 方向 | 客户端主动 Browse/Read/Subscribe | 发布订阅，天然多对多 |
| 载荷 | 结构化、带类型和质量码 | 你自己定（通常 JSON） |
| 穿透防火墙 | 差（要开 4840 入站） | **好**（设备主动外连 1883/8883） |
| 弱网 | 会话重连较重 | 轻量，专为弱网设计 |
| 扩散 | 一对多要 N 个会话 | Broker 天然扇出 |

**所以组合起来最合理**：

```
车间层                    上云
PLC / 仪表 ──OPC UA──▶ 边缘网关 ──MQTT──▶ 云平台
           语义统一          高效搬运
           自描述模型        穿透 NAT
```

**一句话版本**："OPC UA 解决**在车间里说清楚这是什么**，MQTT 解决**把它便宜可靠地送出去**。前者强在语义，后者强在传输和扩散。让 OPC UA 直连公网既不安全也扛不住扇出，所以现场普遍是 UA 采、MQTT 上云。"

> 补充一句能加分的：OPC UA 后来也出了 **PubSub** 规范（可以跑在 MQTT 之上），把 UA 的信息模型和 MQTT 的传输结合起来。知道这件事说明你关注过规范演进。
