## 一、时序数据的三个特征

1. **写多读少**，而且**只追加不更新**
2. **按时间范围查**，几乎从不按主键单点查
3. **相邻数据高度相似**——温度这一秒 25.3，下一秒大概率还是 25.3

第三条是时序库能把数据压到 1/10 的全部原因：**列式存储 + 差值编码 + 压缩**。行式数据库（MySQL）做不到，因为它把不同类型的字段混在一行里。

## 二、超级表：一类设备一张，一台设备一张子表

TDengine 的核心概念，**这个模型理解了这周就过了一半**。

```sql
-- 超级表 = 模板：定义列（随时间变的量）和标签（不变的属性）
CREATE STABLE meter (
    ts        TIMESTAMP,
    temp      FLOAT,
    humidity  FLOAT,
    quality   TINYINT
) TAGS (
    site      BINARY(16),
    line      BINARY(16),
    device_id BINARY(32),
    model     BINARY(32)
);

-- 每台设备一张子表，自动继承结构
CREATE TABLE meter_line1_001 USING meter
    TAGS ('cd-plant', 'line1', 'line1-meter-001', 'XY-THS-485');
```

**为什么一台设备一张表**（而不是全塞一张大表）：

- 同一台设备的数据在磁盘上**物理相邻**，按设备查时几乎是顺序读
- 压缩率更高——同一台设备的温度序列相似度远高于混在一起的
- 删除一台设备 = 删一张表，不用扫全表

**标签（TAGS）和列的区别**：标签**不随时间变**，存在元数据里，不占每行的空间。按标签过滤（`WHERE line='line1'`）是**先筛表再扫数据**，代价极低。

> **建模时最常见的错误**：把 `device_id` 放进列而不是标签。这样每一行都要存一遍设备 ID，且按设备过滤要全表扫描。

## 三、容量估算（M4 闸门要在白板上算）

**题目**：500 设备 × 20 点位 × 1 秒周期，存一年要多少磁盘？

```
每秒行数 = 500 × 20 = 10,000 行/秒

每天  = 10,000 × 86,400        = 8.64 亿行/天
每年  = 8.64亿 × 365           ≈ 3,154 亿行

单行原始大小（宽表：一台设备一行装 20 个点位）
  ts 8 + 20 个 float × 4 + quality 1 ≈ 89 字节
  实际按 500 设备 × 1 行/秒计：500 × 86400 = 4,320 万行/天
  原始 = 4,320 万 × 89 ≈ 3.8 GB/天

压缩后（时序库典型 5–10 倍，取 8）
  ≈ 480 MB/天  →  约 175 GB/年
```

**两种建模的差异要讲清楚**：

| 建模 | 行数/天 | 说明 |
|---|---|---|
| **宽表**（一台设备一行，20 列） | 4,320 万 | 时间戳只存一份，**推荐** |
| **窄表**（一个点位一行） | 8.64 亿 | 时间戳存 20 遍，行数多 20 倍 |

窄表灵活（点位可以随时增减），宽表省空间且查询快。**工业场景通常一台设备的点位是固定的，选宽表。**

**分层保留策略**（这是答案的第二半）：

| 层 | 精度 | 保留 | 大小 |
|---|---|---|---|
| 原始 | 1 秒 | 30 天 | ~14 GB |
| 分钟级 | 1 分钟均值/最值 | 1 年 | ~3 GB |
| 小时级 | 1 小时聚合 | 3 年 | ~0.15 GB |

**一年 175GB 降到 17GB 左右。** 依据是"超过一个月的秒级数据对生产分析没有意义"——这个理由要能讲出来。

## 四、写入性能：批量是数量级差异

```csharp
// ✗ 逐条：每条一次网络往返
foreach (var m in batch) await conn.ExecuteAsync($"INSERT INTO {m.Table} VALUES(...)");

// ✓ 多表批量：一条 SQL 写多张子表
// INSERT INTO t1 VALUES(...)(...)  t2 VALUES(...)(...)
```

**本周要实测并记下三个数字**：单条 TPS、批量 TPS、参数绑定 TPS。这三个数字是面试时"你做过性能测试吗"的直接答案。

典型量级（树莓派上会低不少）：单条几千 TPS，批量能到几十万。**差两个数量级**，所以接入服务必须攒批——W18 会正式做。

**攒批的两个触发条件**：
- 攒够 N 条（比如 1000）
- 或攒够 T 毫秒（比如 200ms）

只按条数会在低流量时延迟很大，只按时间在高流量时批太小。**两个都要。**

## 五、降采样与保留

```sql
-- 降采样查询：这是看板拉一年曲线的正确姿势
SELECT _wstart, AVG(temp), MAX(temp), MIN(temp)
FROM meter
WHERE line = 'line1' AND ts >= NOW - 7d
INTERVAL(1m);
```

**看板绝不能直接拉原始点。** 一周的秒级数据是 60 万点，浏览器画不动，也没有意义——屏幕只有 2000 个像素。`INTERVAL` 让数据库做聚合，传回来的只有几百个点。

**保留策略**：

```sql
CREATE DATABASE iiot KEEP 30 DURATION 1 BUFFER 256;
-- KEEP 30：只保留 30 天，过期自动删
-- DURATION 1：每个数据文件覆盖 1 天，删除时按文件整个丢弃，代价极低
```

配合**流式计算**自动生成分钟级表，实现上面的分层。

## 六、TDengine vs InfluxDB（本周要写一页对比）

| | TDengine | InfluxDB |
|---|---|---|
| 数据模型 | 超级表 + 子表 + 标签 | measurement + tags + fields |
| 查询语言 | **标准 SQL** | Flux（2.x）/ InfluxQL |
| 一设备一表 | **是**（核心设计） | 否 |
| 集群 | 社区版支持 | 2.x 社区版单机 |
| 中文文档 | **质量很高** | 英文为主 |
| 国内工业圈 | **主流选择** | 较少 |

**选 TDengine 的理由要具体**："SQL 上手快、一设备一表的模型和工业场景天然吻合、中文文档和社区响应快、国内工业项目里更常见所以运维找得到人。" 这比"因为它快"有说服力。
