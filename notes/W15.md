## 一、四个概念，必须分清

ThingsBoard 把设备数据切成四类，**这套切法是行业通用的**，不是它独有的：

| 概念 | 中文 | 特征 | 例子 |
|---|---|---|---|
| **Telemetry** | 遥测 | **带时间戳的序列**，只追加，量大 | 温度、电流、产量 |
| **Attributes** | 属性 | **当前值，无历史**（或只留最新） | 固件版本、安装位置、采集周期 |
| **RPC** | 远程调用 | 请求–响应，有超时 | 让设备立刻上报一次、重启设备 |
| **Shadow** | 设备影子 | 期望状态 vs 实际状态 | 想把周期改成 5s，设备离线时先记着 |

**属性再分三种**（这个区分很实用）：

- `client-side`：设备上报的（固件版本）
- `server-side`：平台配的，设备看不到（安装位置、负责人）
- `shared`：平台下发、设备可读的（采集周期）——**这就是配置下发的通道**

**设备影子解决的问题**：设备离线时你改了配置，改动先存在"期望状态"里；设备上线后自动同步，然后"实际状态"回写确认。**没有影子，离线期间的指令就丢了。**

> 你 W8 做的"通过 MQTT 下发远程配置"，就是一个简化版的 shared attributes；如果加上离线暂存和上线同步，就是影子。**这个对应关系要能说出来。**

## 二、规则链：平台的可视化编排

数据进来 → 判断 → 动作，用拖拽的方式连起来：

```
[Message Type Switch]
      ├─ Post Telemetry ─▶ [Save Timeseries] ─▶ [Filter: temp > 80]
      │                                              ├─ True ─▶ [Create Alarm] ─▶ [Send Email]
      │                                              └─ False ─▶ [Clear Alarm]
      └─ Post Attributes ─▶ [Save Attributes]
```

**值得学的是这个思路**，不是这个产品：把"数据流经的处理步骤"显式化。你自己的接入服务（W18）也该有类似的分层——接收 → 校验 → 去重 → 入库 → 告警判定 → 通知，每一步可测、可替换。

## 三、我自建的和 ThingsBoard 差在哪（Q26，面试必问）

**先诚实承认它强在哪**：

| ThingsBoard 强 | 说明 |
|---|---|
| 开箱即用 | 半天能跑通设备接入到仪表盘 |
| 多租户与权限 | 完整的租户/客户/用户体系 |
| 规则链 | 可视化编排，不写代码改逻辑 |
| 仪表盘编辑器 | 拖拽，比 Grafana 更贴 IoT |
| 生态 | OTA、影子、告警、报表都有 |

**再说自建的理由**（要具体，不能是"想自己写"）：

1. **协议落地能力**。ThingsBoard 的强项在**云侧**；它不会帮你处理 485 总线上的字序错乱、终端电阻缺失、Modbus 异常码。**边缘侧的脏活是自建部分的真正价值**——这也是你整个 M1–M3 在做的事。
2. **断网续传的可控性**。平台侧的 SDK 通常假设网络还行。W7 那套"落盘 → 按序补传 → 限流混流"是现场刚需，但每家的策略不一样，用别人的就得迁就它。
3. **点表与工程化**。现场交付要 Excel 导入几千个点位、要热更新、要按客户定制。这是**项目型交付**的需求，平台产品往往覆盖不到。
4. **成本与数据主权**。很多工厂不接受数据出厂区。私有化部署 ThingsBoard 也行，但许可和运维成本要算进去。

**最诚实、也最能打动人的答案**：

> "如果客户只要一个标准的设备监控平台，我会直接上 ThingsBoard 或组态软件，自己写没有性价比。我自建的价值在**边缘侧**——把老设备的 Modbus/S7 采稳、断网不丢数、点表能配置化交付。云侧我甚至可以把数据推给 ThingsBoard，两者不冲突。我做这套完整链路，是因为**只有把两端都走一遍，才知道边界在哪**。"

**这个回答的高明之处**：它承认了工具的价值，划清了自己的定位，还解释了为什么要全做一遍。比"自研更灵活"这种空话强太多。

## 四、和组态软件（组态王 / WinCC / 力控）的区别

面试有时会拿组态软件比，一起准备：

| | 组态软件 | 自建 .NET 方案 |
|---|---|---|
| 开发方式 | 拖拽画面 + 脚本 | 写代码 |
| 上手 | 快 | 慢 |
| 定制上限 | **低**（脚本能力有限） | 高 |
| 跨平台 | Windows | Linux / ARM |
| 大规模 | 几千点还行，上万点吃力 | 看你怎么设计 |
| 版本管理/CI | 几乎没有 | Git + 自动化测试 |
| 价格 | 按点数授权，很贵 | 人力成本 |

**关键差异是"工程化"**：组态软件的工程文件是二进制的，没法 code review、没法自动化测试、没法灰度发布。你的方案能。**这一点对懂软件工程的面试官很有说服力。**
