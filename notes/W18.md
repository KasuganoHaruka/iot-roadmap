# W18 · 平台层整合

> 题库: Q12, Q28

边缘把数据送出来了，这周让平台侧接得住、存得下、判得出告警。

---

## 一、接入服务：订阅 → 攒批 → 写库

```csharp
// 共享订阅，多实例可水平扩容（W6 讲过）
await mqtt.SubscribeAsync("$share/ingest/iiot/+/+/+/telemetry", MqttQualityOfServiceLevel.AtLeastOnce);

// 攒批：两个触发条件缺一不可
var batch = Channel.CreateBounded<Measurement>(50_000);
// 满 1000 条 或 满 200ms 就写一次
```

**两个触发条件的理由**（W13 讲过）：只按条数，低流量时最后几条要等很久；只按时间，高流量时批太小浪费。

**写入失败怎么办**：不能直接丢。落到一个本地重试队列，指数退避重投。**如果 TDengine 挂了 10 分钟，这 10 分钟的数据必须还在**——否则边缘侧辛苦做的断网续传，在平台侧被浪费了。

## 二、告警引擎：五个维度

```csharp
public sealed record AlarmRule(
    string DeviceId, string Tag,
    double? High, double? Low,          // 阈值
    TimeSpan Duration,                  // 持续多久才触发（去抖）
    double Hysteresis,                  // 回差
    AlarmLevel Level);                  // 提示 / 警告 / 严重
```

**状态机**（比一个 if 复杂，但少了它告警就没法用）：

```
Normal ──值越限──▶ Pending ──持续 Duration──▶ Active ──▶ 发通知
   ▲                  │                          │
   │              值回到正常                  值回到 (阈值−回差)
   └──────────────────┴──────────────────────────┘
                                             发恢复通知
```

**`Pending` 这一档是关键**：值刚越限时不立刻报警，先观察 `Duration`。这一档砍掉了 90% 的误报。

**回差（Hysteresis）**：触发 80，恢复 78。没有回差，值在 79.9–80.1 抖动时状态会疯狂翻转，一分钟几十条通知。

**分级不是装饰**：
- 提示——记录，不通知
- 警告——工作时间通知
- 严重——立刻通知，可能触发联锁

**告警要落库**，字段至少：设备、点位、级别、触发时间、触发值、恢复时间、确认人、确认时间。**"上个月这台设备报了几次警"要答得出来。**

## 三、时间戳策略：边缘为主，平台为辅（Q12）

W8 讲过原理，这周落地成表结构：

```sql
CREATE STABLE meter (
    ts          TIMESTAMP,   -- 边缘采集时间，主时间戳
    received_at TIMESTAMP,   -- 平台接收时间
    temp        FLOAT,
    quality     TINYINT
) TAGS (site BINARY(16), line BINARY(16), device_id BINARY(32));
```

**`ts` 必须是边缘时间**——否则断网补传时，一小时的数据会全挤在恢复后的几秒里，曲线彻底废掉。

**`received_at` 的用途**：
- 算端到端延迟：`received_at - ts`
- 识别补传数据：延迟远大于正常值的就是补传的
- 排查时钟漂移：某台设备的 `ts` 持续超前/落后

**时钟漂移的处理**：

```csharp
var skew = receivedAt - ts;
if (Math.Abs(skew.TotalMinutes) > 5)
{
    log.Warning("设备时钟偏差 {DeviceId} {SkewMinutes}", deviceId, skew.TotalMinutes);
    // 打标记，但不要改写数据——改了就再也查不出问题在哪
}
```

**"打标记但不改写"是重要的工程判断**：静默修正会掩盖真问题，等到有人发现数据对不上时已经无从追溯。

## 四、乱序写入：补传与实时混流

断网恢复后，补传的老数据和新采的实时数据**同时涌向平台**。

```
时间轴 →
实时:                                    [12:00][12:01][12:02]
补传: [11:00][11:01]...[11:30]
到达顺序: 11:00, 12:00, 11:01, 12:01, 11:02, ...   ← 完全乱序
```

**时序库能不能接受乱序写入**：TDengine 可以（有乱序写入窗口），但**乱序会显著降低写入性能和压缩率**——它要回头改已经落盘的数据块。

**三个应对手段**：

1. **边缘侧限流补传**（W7 讲过）：补传和实时按 1:3 交替，乱序范围可控
2. **平台侧按时间窗口排序**：接入服务攒批时按 `ts` 排一下再写，把批内的乱序消掉
3. **配置乱序窗口**：TDengine 的数据库参数允许指定能接受多久的乱序数据；超出窗口的会被拒绝——**这个窗口必须 ≥ 你的最大断网时长设计值**

## 五、一条数据的完整生命周期（Q28，面试压轴题）

**能完整讲一遍，就证明整个系统你是自己搭的。**

```
① 采集     Modbus 读回原始寄存器 → 按字序解析 → 缩放 → 打边缘时间戳 + 质量码
              防丢：读失败不写入，标记 Bad 质量，统计计入失败率

② 缓冲     写 SQLite（seq 自增, sent=0），事务批量提交
              防丢：先落盘再发送；synchronous=NORMAL，断电最多丢最后几条

③ 上报     按 seq 取未发送的批，MQTT QoS1 发布
              防丢：收到 PUBACK 才标记 sent=1；没收到就重发（可能重复）

④ 传输     EMQX 接收
              防丢：Broker 持久化会话，订阅端离线时消息不丢

⑤ 接入     共享订阅消费 → 按 seq 去重 → 攒批
              防重：seq 回退丢弃 + 消息 ID 去重窗口

⑥ 入库     批量写 TDengine，主键 (子表, ts)
              防重：同一时间戳覆盖，天然幂等
              防丢：写失败进重试队列，指数退避

⑦ 告警     阈值 + 持续时间 + 回差 → 落库 + 通知

⑧ 保留     原始 30 天 → 分钟级 1 年 → 小时级 3 年
```

**每一步都要说清"这一步靠什么保证不丢/不重"**。这道题答得完整，面试基本就稳了。
