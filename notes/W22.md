# W22 · 面试训练

> 题库: Q35

**学得会讲不出，是这条路上最常见的死法。** 这周不学新东西，只练"说"。

---

## 一、题库出声过一遍（本周主线）

打开「重测」，35 道题**每题出声讲一遍**。不是默读，是**发出声音**。

**为什么必须出声**：默读时大脑会自动跳过卡壳的地方，产生"我会了"的错觉。出声会强制你把每个逻辑接缝都补上——**卡壳的地方就是你没真懂的地方**。

用应用里的三档评分诚实标记：
- **不会** → 当天回来再测
- **模糊** → 明天再测
- **会** → 推到 1 → 3 → 8 天后

**标准是能对着白板讲，不是"看过"。** 这句话你自己写在路线图里。

---

## 二、白板画架构图 ×5

限时 5 分钟，白纸默画，讲完整条链路。练 5 次，每次记录漏了什么。

**讲的顺序**（照这个走不会乱）：

1. **从右往左先讲一遍需求**："客户要看到每台设备的实时数据和历史趋势，断网不能丢数据。"
2. **从左往右讲实现**：设备 → 协议 → 网关 → MQTT → 接入 → 时序库 → 展示
3. **在每一段停下来讲一个取舍**：
   - 为什么自研 Modbus 驱动而不用 NModbus
   - 为什么边缘要落盘而不是靠 QoS
   - 为什么主时间戳是边缘时间
   - 为什么 TDengine 不是 MySQL
4. **最后讲边界**："这套单机能扛 200 台，再多要拆接入服务，我留了共享订阅的口子但没验证过。"

**面试官真正在听的是第 3 步。** 画得出图的人很多，讲得出"为什么不那样做"的人少。

## 三、三个踩坑故事（必须准备）

**故事比结论有说服力一百倍。** 准备三个，各一分钟，覆盖三个层面：

**① 协议层**——32 位浮点乱码
> 现场读温度出来是天文数字。查了半天不是代码问题，是字序。设备手册压根没写字序。我让现场把温度调到一个已知值 25.5，把 4 个字节的四种排列各算一遍，发现是 CDAB。后来我把字序做成了点表里的每点可配，因为一条总线上不同品牌的仪表可能不一样。

**② 可靠性**——随机丢包
> 有一段时间通信成功率在 90% 上下飘，时好时坏。不是软件问题——现场为了保险，在三台设备上都装了 120Ω 终端电阻。三个并联下来 40Ω，驱动器带不动，信号幅度不够。拆掉中间那个就好了。这件事之后我在系统里加了"通信质量劣化"这一档告警，成功率掉到 98% 以下就提示，不用等它彻底断。

**③ 现场/协作**——不让改 PLC 程序
> 客户不同意动 PLC 程序，理由是改了要重新验证整条产线。我的做法是先只读现有的 DB 地址，完全不碰程序；确实需要新增的量，申请加一个不被任何逻辑引用的只读 DB，评审时的说服点是"不改变任何既有扫描逻辑"。最后批下来了。

**每个故事的结构**：现象 → 排查过程 → 根因 → **后来我改了什么**。最后那半句是精髓——它说明你从坑里学到了东西，而不只是修好了。

## 四、反问：面试的下半场

面试官问"你有什么想问的吗"，答"没有"等于放弃了一半的信息。

**问这些**（都能帮你判断这家值不值得去）：

| 问题 | 你在探什么 |
|---|---|
| 团队现在几个人？软件和电气怎么分工？ | 你是唯一的软件？那没人带你 |
| 现有系统是自研还是用组态软件？技术债多吗？ | 进去是新建还是填坑 |
| **出差比例大概多少？主要去哪些地方？** | **工业岗位这条必问**，直接影响生活 |
| 一个项目从接到交付大概多久？ | 项目节奏和加班强度 |
| 团队用什么方式管理代码和版本？ | 有没有基本的工程规范 |
| 我这样的背景，你觉得最需要补的是什么？ | **这个问题会让对方认真回答，而且是免费的诊断** |

**最后一个问题的价值最高**：即使这家没成，你也拿到了一份"还差什么"的清单——这正是 M6 闸门的第二条。

## 五、模拟面试一场

**找人陪练**（朋友、社区、或 AI）。规则：

- 全程 45 分钟，不许翻笔记
- 对方从题库里随机抽 10 题
- **必须包含一次"白板画架构"**
- 结束后立刻写复盘：哪题卡了、卡在哪、怎么补

**录音**。回放时你会听到自己的口头禅、逻辑跳跃、和"这个……那个……"——这些在真实面试里都是扣分项，但你自己讲的时候完全察觉不到。

## 六、带团队的问题（Q35）

10 年经验会被问这个。**三人小组做这套系统，怎么分工排期**：

> **分工按接口切，不按人切。**
>
> - A 负责**边缘侧**：驱动 + 采集调度 + 本地缓冲
> - B 负责**平台侧**：接入服务 + 时序库 + 告警
> - C 负责**展示侧**：Grafana + WPF 上位机
>
> **第一周三个人一起把接口定死**：`IDeviceDriver` 的方法签名、MQTT 的主题规范和载荷 schema、数据库表结构。定完之后各自可以并行，靠 mock 数据自测，不用互相等。
>
> **风险最高的是 A 的协议对接**（现场不确定性最大），所以我会让 A 先做，并且第 2 周就安排一次真实设备的联调，把不确定性尽早暴露。
>
> **我自己会同时做 A 和整体架构**——协议层是这个系统最难的部分，我不会把最难的交给别人然后自己去写界面。

**这个回答里有三个信号**：接口先行（工程习惯）、风险前置（项目管理）、自己啃最难的（技术领导力）。
