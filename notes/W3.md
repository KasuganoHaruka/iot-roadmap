## 一、先分层，再写码

一上来就写 `ModbusRtuClient` 和 `ModbusTcpClient` 两个类，就会把编解码抄两遍。W2 已经给了答案：**RTU 和 TCP 唯一真正不同的，只有外壳和校验**，中间的 PDU 完全一样。

```
       ModbusDriver          ← 功能码语义、重试、异常映射、批量读规划
            │
     IModbusTransport        ← 只负责「把 PDU 送出去，把 PDU 收回来」
        ╱        ╲
  RtuTransport   TcpTransport
  加从站地址+CRC   加 MBAP 头
  按字节计数分帧   按长度字段分帧
```

接口窄到只剩一个方法就对了：

```csharp
public interface IModbusTransport
{
    Task OpenAsync(CancellationToken ct = default);
    Task CloseAsync(CancellationToken ct = default);
    /// 送出 PDU，返回响应 PDU（外壳和校验由实现自己处理掉）
    Task<byte[]> SendAsync(byte unitId, ReadOnlyMemory<byte> pdu, CancellationToken ct = default);
}
```

**这个分层本身就是面试素材。** "我把传输层抽象出来，所以加 TCP 只写了 40 行"——比"我会用 NModbus"有力得多。

## 二、超时怎么定（面试常问）

不要拍脑袋写 `Timeout = 1000`。超时应该由**物理量**推出来：

```
理论传输时间 = 总字节数 × 11 bit/字节 ÷ 波特率
```

RTU 每字节是 11 位（1 起始 + 8 数据 + 1 校验 + 1 停止）。9600bps 下一个 8 字节请求 ≈ 9ms，一个读 10 寄存器的 25 字节响应 ≈ 29ms。

**实际超时 = 理论时间 × 系数 + 从站处理时间。** 工程经验：

| 场景 | 建议超时 |
|---|---|
| RTU 9600，小报文 | 300–500ms |
| RTU 9600，读满 125 寄存器 | 800ms–1s |
| TCP 局域网 | 200–500ms |
| 经 4G / DTU 透传 | **2–5s**，且要留意透传模块自己的缓存延迟 |

> 定太短：正常设备被判超时，重试风暴把总线塞死。
> 定太长：一台掉线的设备拖慢整轮扫描——这就是 W4 要解决的"慢设备隔离"。

**重试次数 2–3 次足够**，且重试之间要有间隔（否则等于把故障设备的问题放大三倍）。重试前必须 `DiscardInBuffer()`，防止上一次的半截响应污染下一次。

## 三、异常码要转成业务异常，不能吞

```csharp
public sealed class ModbusExceptionResponse : Exception
{
    public byte FunctionCode { get; }
    public byte ExceptionCode { get; }
    public ModbusExceptionResponse(byte fc, byte code)
        : base($"从站返回异常：功能码 0x{fc:X2}，异常码 {code}（{Describe(code)}）")
        => (FunctionCode, ExceptionCode) = (fc, code);

    static string Describe(byte c) => c switch
    {
        0x01 => "非法功能码——设备可能不支持这个功能码",
        0x02 => "非法数据地址——地址越界，或 4xxxx 记法没减 1",
        0x03 => "非法数据值——数量超上限，或写入值超范围",
        0x04 => "从站设备故障",
        0x06 => "从站忙，稍后重试",
        _    => "未定义异常码",
    };
}
```

**关键判断**：异常响应**不该重试**（重试一百次地址还是越界），但超时**应该重试**。把这两类分开，是"写过驱动"和"抄过代码"的分水岭。

## 四、批量读优化（本周的加分点）

现实中的点表是这样的：地址 0、1、2、5、6、20、21、100。天真做法发 8 个请求；聪明做法合并成 3 个。

**算法**：按区（保持寄存器/输入寄存器不能混）分组 → 地址排序 → 贪心合并，两个约束：

1. **跨度上限**：合并后 `endAddr - startAddr + 1 ≤ 125`
2. **空洞代价**：两个地址之间的空洞如果太大，合并反而更亏——多读的寄存器也是要占带宽的

```
地址: 0 1 2 . . 5 6 . . . . . . . . . . . . 20 21 ......... 100
      └─合并成 0..6（读7个，浪费2个）─┘   └─21..22─┘      └─单读─┘
```

**空洞阈值怎么定**：一个请求的固定开销（帧头 + CRC + 从站处理 + 帧间隔）大约相当于传 10–20 个寄存器的时间。所以**空洞小于 ~10 个寄存器就合并，大于就切开**，把这个阈值做成可配置项。

> 面试话术："我按最大跨度和空洞阈值两个条件做贪心合并，把 200 个离散点位从 200 个请求压到 12 个，轮询周期从 6 秒降到 400 毫秒。"——**数字要真的测出来**，W4 会有真实总线可以量。

你仓库里 `ReadPlanner.cs` 的 6 个测试就是这件事：合并相邻、大空洞切分、不跨区合并、尊重上限、乱序输入、多寄存器类型。

## 五、字序：四种排列，做成配置

两个 16 位寄存器拼一个 32 位值，有四种排法：

| 字序 | 寄存器排列 | 常见于 |
|---|---|---|
| **ABCD** | 高字在前，字节内高位在前（大端） | 标准，规范默认 |
| **CDAB** | 字交换（word swap） | **最常见的"非标"**，很多国产仪表 |
| **BADC** | 字节交换 | 少见 |
| **DCBA** | 完全反转（小端） | 少见 |

**现场排查方法**：让设备输出一个**已知值**（比如把温度调到 25.5），把读到的 4 个字节按四种排列各算一遍，哪个等于 25.5 就是哪种。**不要试图从手册推**——很多手册压根没写。

所以驱动必须把字序做成**点表里的每点可配**，不是全局写死：一条总线上挂不同品牌的仪表，字序可能就不一样。

## 六、测试怎么写

覆盖率 70% 是底线，但更重要的是**覆盖对了地方**：

- **CRC**：规范里的校验向量 + 随机数据下逐位法与查表法一致
- **字序**：四种排列 × 编码解码往返（`Encode(Decode(x)) == x`）
- **编解码**：请求构造、响应解析、字节计数校验
- **异常路径**：异常响应能抛出正确的异常类型；CRC 错误被识别；响应长度不足被识别
- **批量读规划**：上面那 6 个场景

> 传输层用**假实现**测，不要连真设备。`FakeTransport` 收到什么 PDU 就返回预置的响应字节，这样异常路径（CRC 错、超时、半帧）才构造得出来。真设备上你**没法**让它返回一个 CRC 错误的帧。
