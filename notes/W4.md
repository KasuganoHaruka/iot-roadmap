# W4 · 轮询调度与真实总线

> 题库: Q9, Q10, Q30

驱动写好了，但一条总线上挂三台设备、其中一台掉线时会发生什么？这周解决的是**这台拖不垮那台**。M1 的闸门在本周末。

---

## 一、总线是独占的，这是一切设计的前提

485 是**半双工共享介质**：同一时刻只能有一个请求在飞。所以"并发采集 10 台设备"在一条 485 总线上是**不存在**的——只能排队。

由此推出两条铁律：

1. **一条总线一个调度线程**，请求串行发出。多线程往同一个串口写 = 报文交错 = 全乱。
2. **任何一次超时都在花掉整条总线的时间**。一台设备超时 500ms×重试 3 次 = 1.5 秒，这 1.5 秒里其他设备一个字节都发不出去。

TCP 就没这个约束（每台设备一条 socket，可以并发），所以调度器要能区分"共享总线"和"独立链路"两种拓扑。

---

## 二、轮询周期怎么定（面试常问）

先算**一轮扫描的理论时间**：

```
单次事务 = 请求传输 + 从站处理 + 响应传输 + 帧间隔(3.5字符)
```

9600bps、读 20 个寄存器、5 台设备：

```
请求 8 字节  ≈ 9ms
响应 45 字节 ≈ 52ms
从站处理     ≈ 10–50ms（看设备，廉价仪表能到 100ms）
帧间隔       ≈ 4ms
────────────────────
单台 ≈ 75–115ms   ×5 台 ≈ 400–600ms
```

**所以这条总线的物理下限就是 ~600ms，你设 100ms 周期是自欺欺人**——队列只会越积越长。

**定周期的方法**：
1. 先测出一轮实际耗时（W4 的统计功能就是干这个的）
2. 周期 ≥ 一轮耗时 × 1.5，留出重试和抖动的余量
3. **按数据的实际变化速率分级**：温度 5 秒一次足够，产量计数 1 秒，报警位 200ms

分级比统一提速有效得多——把 80% 的慢点位降到 5 秒，快点位才有带宽。

> 面试话术："我按点位的物理变化速率分三档周期，把总线占用率从 95% 降到 40%，关键报警点的响应从 6 秒降到 300 毫秒。"

**总线占用率**是个好指标：`一轮实际耗时 ÷ 轮询周期`。超过 70% 就该考虑分总线或降频了。

## 三、慢设备隔离

一台设备掉线，不能让它每轮都吃掉 1.5 秒。

**熔断三态**，和 Polly 的模型一致（W8 会正式用上 Polly）：

```
Closed（正常）
   │ 连续失败 N 次（建议 3）
   ▼
Open（熔断）——本轮直接跳过，不发请求，不花总线时间
   │ 冷却时间到（指数退避）
   ▼
HalfOpen（试探）——只放一个请求过去
   ├─ 成功 → Closed，退避计时器归零
   └─ 失败 → 回 Open，退避时间翻倍
```

**指数退避**：`1s → 2s → 4s → 8s → 16s → 30s 封顶`。封顶很重要，否则设备修好了要等几十分钟才被发现。

再加**抖动**（jitter，退避时间上下随机 ±20%）：五台设备同时掉线时，避免它们的重连时刻完全对齐，形成周期性的总线拥塞。

## 四、掉线检测：怎么快，又怎么不误判（面试常问）

**一次超时不算掉线。** 现场干扰导致偶发 CRC 错、偶发超时是常态，单次失败就报警，运维会被告警淹没到关掉通知。

判定用**双阈值**：

| 判据 | 建议 |
|---|---|
| 掉线 | 连续失败 ≥ 3 次 **且** 持续 ≥ 10 秒 |
| 恢复 | 连续成功 ≥ 2 次（防止刚通就又断的抖动） |

"连续 N 次"和"持续 T 秒"要**同时满足**：只看次数，快周期的点位 1 秒就报警；只看时间，慢周期的点位可能一次都没试过。

**质量分级比二值状态更有用**：不要只有"在线/离线"，给每台设备一个滑动窗口成功率（比如最近 100 次）：

- \> 98%：健康
- 90–98%：**劣化**——通常意味着接线松动、终端电阻缺失或干扰，是现场故障的早期信号
- < 90%：故障

**"劣化"这一档是现场价值最大的东西**：它能在设备彻底掉线之前把问题暴露出来。

## 五、通信质量统计：采什么

每台设备维护：

```csharp
public sealed record DriverStatistics
{
    public long Requests { get; init; }
    public long Failures { get; init; }
    public long Timeouts { get; init; }
    public int  ConsecutiveFailures { get; init; }
    public double SuccessRate { get; init; }      // 滑动窗口，不是累计
    public double AvgLatencyMs { get; init; }
    public double P99LatencyMs { get; init; }     // 平均值会骗人，P99 不会
    public DateTimeOffset? LastSuccess { get; init; }
}
```

**为什么要 P99**：平均时延 80ms 看着很好，但如果 P99 是 900ms，说明每 100 次就有一次接近超时——这条总线已经在悬崖边上了，平均值完全看不出来。

这些数字**本身就是上报的数据**（W17 会把它们发到平台），也是你面试时"能拿出数字"的来源。

## 六、《Modbus 现场排错手册》

本周的产出之一，也是**面试谈资的核心**。格式统一写成「现象 → 判断方法 → 处理」：

| 故障 | 现象 | 判断方法 | 处理 |
|---|---|---|---|
| A/B 接反 | 完全收不到，或全是帧错误 | 两根线对调再试（比翻手册快） | 调线 |
| 波特率不匹配 | 收到数据但全是乱码、CRC 恒错 | 从 9600 开始逐档试 | 改配置或改设备拨码 |
| 地址错位 | 读到的值有规律地偏移一格 | 手册是不是 4xxxx 记法？减 1 试试 | 点表统一成协议地址 |
| 字序错 | 32 位值是乱码，16 位值正常 | 让设备输出已知值，四种排列各算一遍 | 点表里改字序 |
| 终端电阻缺失/多装 | **随机丢包**，时好时坏，长线更明显 | 断电测总线两端电阻，应约 60Ω（两个 120Ω 并联） | 只留两端各一个 |
| 从站地址冲突 | 两台设备抢答，数据来回跳变 | 逐台断电，看谁还在应答 | 改拨码 |
| 星型接线 | 距离一长就不稳 | 看走线拓扑 | 改成手拉手菊花链 |
| 地环流 | 干扰随大功率设备启停变化 | 屏蔽层是不是两端都接地了 | 只接一端 |

**每一条你都应该亲手制造一次**。手册里写"我遇到过"和"我听说过"，面试官三个追问就能分辨出来。
