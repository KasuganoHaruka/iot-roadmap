## 一、QoS：三档，各有各的代价

| QoS | 语义 | 报文交互 | 代价 |
|---|---|---|---|
| **0** | 至多一次（fire-and-forget） | PUBLISH | 可能丢 |
| **1** | **至少一次** | PUBLISH → PUBACK | **可能重复** |
| **2** | 恰好一次 | PUBLISH → PUBREC → PUBREL → PUBCOMP | 四次握手，吞吐最低、延迟最高 |

**必做实验**：用 MQTTnet 各发一条，抓包数报文数量。QoS2 的四次交互亲眼看过一次，就再也不会随口说"用 QoS2 最保险"。

**工业现场怎么选**：

- **遥测数据用 QoS 1**。丢一条温度不致命，但重复很常见——所以业务侧必须幂等。
- **控制指令用 QoS 1 + 业务层确认**，不要用 QoS 2。QoS2 的开销换来的"恰好一次"只覆盖到 Broker，管不到你的业务处理。真正的一次性要靠**指令 ID + 执行结果回执**。
- **QoS 0 用在**高频、可丢、有后续值覆盖的场景（比如 100ms 的振动波形）。

## 二、QoS1 为什么会重复，怎么幂等（面试必问）

**重复的成因**：发布端发出 PUBLISH，Broker 收到并投递了，但 PUBACK 在回程丢了。发布端等不到 ACK，**按协议必须重发**。于是订阅端收到两条一模一样的消息。

这不是 bug，是 QoS1 定义的行为。**去重是业务侧的责任。**

三层防线，从便宜到贵：

1. **设备侧单调递增序号**：每条消息带 `seq`，同一设备的 `seq` 严格递增。下游看到 `seq ≤ 已处理最大值` 就丢弃。**这是最有效的一层**，而且顺便解决了乱序。
2. **消息 ID + 去重窗口**：给每条消息一个 UUID，接入服务用一个 5 分钟的 LRU 缓存记住见过的 ID。窗口开多大取决于你的重传窗口。
3. **写入层天然幂等**：时序库按 `(设备, 时间戳)` 做主键，重复写入是覆盖而不是追加。**TDengine 就是这个行为**——同一子表同一时间戳的两条数据，后者覆盖前者。所以到了 M4 这层几乎免费。

> 面试话术："QoS1 的重复来自 PUBACK 丢失后的协议级重传。我在设备侧带单调序号，接入侧按序号丢弃回退，最后落到 TDengine 时 `(设备, 时间戳)` 天然覆盖——三层里任何一层单独都够用，叠起来是为了乱序和补传混流的场景。"

## 三、Retain：谁需要它，坑在哪

**Retain = Broker 为每个主题保留最后一条**，新订阅者一连上立刻收到。

**该用的地方**：设备**状态**（在线/离线、当前配置、点表版本）。看板刚打开就该知道设备现在是什么状态，而不是干等下一次上报。

**坑**：

1. **遥测数据不要 retain。** 你不会想让新订阅者收到一条 3 小时前的温度还以为是当前值。
2. **retain 消息不会自己消失。** 设备下线报废了，那条 retain 还在。清除方法是往同一主题发一条**空载荷（zero-byte payload）的 retain 消息**。
3. **和 LWT 配合才完整**：上线时发 `online` 的 retain，LWT 设成 `offline` 的 retain，这样任何时刻订阅都能拿到正确状态。

## 四、LWT（遗嘱）：设备异常掉线的检测

**正常断开**（客户端发 DISCONNECT）**不触发遗嘱**；**异常断开**（断电、断网、进程被杀）才触发。这个区别是 LWT 存在的全部意义。

```csharp
var options = new MqttClientOptionsBuilder()
    .WithClientId($"gw-{siteId}")
    .WithWillTopic($"iiot/{site}/{line}/{device}/status")
    .WithWillPayload("offline")
    .WithWillRetain(true)
    .WithWillQualityOfServiceLevel(MqttQualityOfServiceLevel.AtLeastOnce)
    .WithKeepAlivePeriod(TimeSpan.FromSeconds(30))
    .Build();
```

**遗嘱多久发出**：Broker 在 **1.5 × KeepAlive** 内没收到任何报文才判定失联。KeepAlive 30 秒 → 最坏 45 秒后才发遗嘱。

**必做实验**：直接 `kill -9` 客户端，掐表看遗嘱多久到。然后把 KeepAlive 改成 10 秒再试一次。**这个延迟就是你的设备离线告警的下限**，做告警设计时必须知道。

> KeepAlive 不是越小越好：4G 网络下太短的心跳会显著增加流量和功耗，也更容易因瞬时抖动误判离线。现场 30–60 秒是常见取值。

## 五、共享订阅：解决什么问题

普通订阅是**广播**：三个接入服务实例订阅同一主题，每条消息**每个都收到一遍**——数据被写三次。

共享订阅 `$share/{group}/{topic}` 是**负载分担**：同组内只有一个消费者收到。

```
iiot/+/+/+/telemetry            ← 三个实例各收全量（错）
$share/ingest/iiot/+/+/+/telemetry  ← 三个实例分摊（对）
```

这是接入服务能水平扩容的前提。**必做实验**：起两个消费者订阅同一个共享组，发 100 条，看是不是各收到约 50 条。

> 注意：共享订阅内部的分发是**按连接**轮询的，不保证同一设备的消息落到同一个消费者。所以如果你的去重依赖"同设备顺序处理"，要么按设备哈希分组，要么把去重放到数据库层。

## 六、主题设计：这周要定下来并写进文档

```
iiot/{site}/{line}/{device}/telemetry     设备 → 平台，遥测
iiot/{site}/{line}/{device}/status        设备 → 平台，状态（retain + LWT）
iiot/{site}/{line}/{device}/cmd           平台 → 设备，指令
iiot/{site}/{line}/{device}/cmd_resp      设备 → 平台，指令回执
```

设计原则：

- **层级从粗到细**，这样 `iiot/site1/#` 能一把订走整个厂区
- **方向写在最后一段**，不要用 `up/down` 这种前缀——通配符会难写
- **不要把可变数据放进主题**（比如把温度值编进主题名）。主题是路由，不是载荷。
- **通配符**：`+` 匹配一层，`#` 匹配剩余所有层且只能在末尾
- 提前想好 ACL：`iiot/{site}/#` 是天然的权限边界

## 七、MQTT / HTTP / CoAP 怎么选

| | MQTT | HTTP | CoAP |
|---|---|---|---|
| 模型 | 发布订阅，长连接 | 请求响应，短连接 | 请求响应，UDP |
| 服务端主动下发 | **原生支持** | 要轮询或 WebSocket | 支持 observe |
| 报文开销 | 最小 2 字节头 | 几百字节头 | 4 字节头 |
| 弱网 | 长连接 + 会话恢复 | 每次重建连接，很贵 | UDP，无连接 |
| 适用 | **设备上云主力** | 配置下发、文件上传、OTA | 极低功耗、NB-IoT |

工业现场 **MQTT 是默认答案**，HTTP 用来传大块（OTA 包、历史文件补传）。
