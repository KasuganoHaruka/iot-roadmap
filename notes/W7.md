# W7 · 断网续传（本月核心）

> 题库: Q11, Q14, Q28

**这一周的产出是你简历上最值钱的一段。** "拔网线 10 分钟，恢复后数据零丢失"这句话，比"熟悉 MQTT"有力一百倍——而且要有录屏。

---

## 一、为什么不能只靠 MQTT 的 QoS

常见误解："我用 QoS1，Broker 会帮我保证送达。"

**不会。** QoS1 保证的是**已建立的连接上**消息不丢。网线一拔，客户端连 Broker 都连不上，QoS 无从谈起。客户端库的内存队列能撑几十秒到几分钟，然后要么 OOM 要么丢弃。

所以**断网续传必须自己做，落到磁盘上**。

---

## 二、状态机：一条数据的完整生命周期

```
采集 ──▶ 写入 SQLite（sent=0, seq 自增）
                │
                ▼
        发送线程按 seq 取未发送的一批
                │
         ┌──────┴───────┐
      发布成功         发布失败/超时
         │                │
    收到 PUBACK      不改任何状态 ──▶ 退避后重来
         │
    标记 sent=1（或直接删）
         │
    定期清理已发送且超过保留期的行
```

**关键设计：先落盘，再发送。** 顺序反了就有一个窗口——数据在内存里等着发，这时断电，数据就没了。

**为什么要自增序号 `seq`**：
1. 补传时能保证**按采集顺序**发出去，不会新数据插到老数据前面
2. 下游按 `seq` 去重（W6 讲的第一层幂等）
3. 断点续传只需记住"发到哪个 seq"

## 三、SQLite 表设计

```sql
CREATE TABLE measurement (
    seq        INTEGER PRIMARY KEY AUTOINCREMENT,
    device_id  TEXT    NOT NULL,
    tag        TEXT    NOT NULL,
    value      REAL    NOT NULL,
    quality    INTEGER NOT NULL,      -- 0=Good 1=Bad 2=Uncertain
    ts         INTEGER NOT NULL,      -- 边缘侧采集时间，Unix 毫秒
    sent       INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX ix_pending ON measurement(sent, seq) WHERE sent = 0;
```

**必开 WAL**：

```csharp
using var conn = new SqliteConnection("Data Source=buffer.db");
conn.Open();
conn.Execute("PRAGMA journal_mode=WAL;");        // 读写不互相阻塞
conn.Execute("PRAGMA synchronous=NORMAL;");      // 见下
```

**`synchronous` 怎么选**（这是个真实的取舍，面试可以聊）：

| 值 | 行为 | 代价 |
|---|---|---|
| `FULL` | 每次提交都 fsync | 最安全，但在 SD 卡上慢到无法接受 |
| `NORMAL` | WAL 模式下只在 checkpoint 时 fsync | **推荐**。断电最多丢最后几条 |
| `OFF` | 交给操作系统 | 断电可能损坏数据库，不要用 |

**部分索引** `WHERE sent = 0` 很关键：待发队列通常只有几十条，而表里可能有几十万行已发送的。全表索引会随数据量一起膨胀，部分索引不会。

**批量写入**：一条一条 `INSERT` 在 SD 卡上会慢到离谱。用**一个事务包住一批**（比如一个采集周期的所有点位），TPS 能差两个数量级。

## 四、背压：内存不能无限涨

采集速度 > 发送速度时（断网就是极端情况），中间队列会一直涨。**必须有界。**

```csharp
var channel = Channel.CreateBounded<Measurement>(new BoundedChannelOptions(10_000)
{
    FullMode = BoundedChannelFullMode.DropOldest,   // 满了丢最旧
    SingleReader = true,
    SingleWriter = false,
});
```

`FullMode` 四个选项对应四种业务决策：

| 选项 | 语义 | 何时用 |
|---|---|---|
| `Wait` | 写入方阻塞 | **采集不能被拖慢，所以不要用** |
| `DropOldest` | 丢最旧的 | 实时性优先（当前值比历史值重要） |
| `DropNewest` | 丢最新的 | 几乎没有合适场景 |
| `DropWrite` | 丢当前这条 | 同上 |

**但队列只是内存里那一层。** 真正的容量在 SQLite：

```
断网 1 小时 × 5 台设备 × 20 点位 × 1 秒周期 = 360 万行
每行约 60 字节 → 约 216 MB
```

**所以必须有磁盘保留策略**：按行数封顶（比如 500 万行）或按时间封顶（比如 24 小时），超了从最旧的删。**并且要在设计时就算出这个数字**——面试官会问"断网三天会怎样"，你要能答"我按 24 小时封顶，超过就丢最旧的，因为超过一天的秒级数据对生产分析已经没有意义"。

## 五、拔网线测试：这周的验收

**测试步骤**（照做，并录屏）：

1. 正常运行，看板上曲线在动
2. **拔掉网线**，掐表
3. 观察：本地 SQLite 行数在涨，**内存曲线平稳**（这一条最重要）
4. 等 10 分钟
5. **插回网线**
6. 观察：积压数据按序补传，看板上曲线**从断点处接上**，不是从当前时刻开始

**验收标准**：

- [ ] 数据零丢失（断网期间的每一条都到了平台）
- [ ] 顺序正确（补传的数据按采集时间排列，不是乱序）
- [ ] 无重复，或下游能去重
- [ ] 内存在断网 1 小时内不无限增长
- [ ] 补传不会把实时数据饿死（见下）

**补传与实时混流**：断网 10 分钟积压 12000 条，恢复后如果先把这 12000 条全发完再发新数据，看板会有几分钟看不到当前值。**做法是限流补传**：每批发 500 条，中间穿插当前批次的新数据，让实时和补传按比例（比如 1:3）交替。这个细节面试官很爱问。
