## 一、Polly：重试、熔断、超时的组合

W4 手写过一个熔断器，这周换成 Polly 的正规实现，并且**理解组合顺序**。

```csharp
var pipeline = new ResiliencePipelineBuilder()
    .AddTimeout(TimeSpan.FromSeconds(5))            // 最外层：总时限
    .AddRetry(new RetryStrategyOptions
    {
        MaxRetryAttempts = 3,
        BackoffType = DelayBackoffType.Exponential,
        UseJitter = true,                            // 避免重连风暴对齐
        Delay = TimeSpan.FromSeconds(1),
    })
    .AddCircuitBreaker(new CircuitBreakerStrategyOptions
    {
        FailureRatio = 0.5,
        MinimumThroughput = 10,
        SamplingDuration = TimeSpan.FromSeconds(30),
        BreakDuration = TimeSpan.FromSeconds(30),
    })
    .Build();
```

**顺序是有讲究的**：超时在最外层意味着"整个重试过程"受这个时限约束；如果放最内层，则是每次尝试各有时限。两种都对，但**你要说得清自己选的是哪种、为什么**。

**熔断器不该包住什么**：不要给"写本地数据库"加熔断。熔断是保护**下游**的，本地磁盘没有需要保护的对象，失败了只能重试或告警。

## 二、健康检查端点

现场运维不会读你的日志，他们会问"这玩意儿是好的吗"。给一个 URL。

```csharp
app.MapGet("/health", () => Results.Json(new
{
    status      = overall,                    // healthy / degraded / unhealthy
    uptime      = DateTime.UtcNow - started,
    broker      = mqtt.IsConnected,
    backlog     = buffer.PendingCount,        // 积压条数——最有用的一个数
    devices     = drivers.Select(d => new {
        d.Id, d.Online, d.SuccessRate, d.P99LatencyMs, d.LastSuccess }),
    lastCollect = lastCollectAt,
}));
```

**`backlog`（积压条数）是最有价值的单一指标**：它同时反映了网络、Broker、平台三方的健康。积压持续上涨 = 下游出问题了，比任何单项检查都灵。

分三档而不是两档：**healthy / degraded / unhealthy**。"有一台设备离线但其余正常"是 degraded，不是 unhealthy——二值状态会让运维疲于奔命。

## 三、优雅退出：退出前把缓冲刷盘

```csharp
public sealed class GatewayService(IHostApplicationLifetime life, IMeasurementBuffer buffer)
    : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        life.ApplicationStopping.Register(() => { /* 停止采集，不再接新数据 */ });
        // ...
    }

    public override async Task StopAsync(CancellationToken ct)
    {
        await buffer.FlushAsync(ct);        // 内存队列里的全部落盘
        await base.StopAsync(ct);
    }
}
```

**systemd 的配合**：`TimeoutStopSec=30`。默认 90 秒，太长——服务重启时运维会以为卡死了；太短则刷盘没做完就被 `SIGKILL`。

**必测**：跑着的时候 `systemctl restart`，检查重启前后 SQLite 的行数连不连得上。这是"优雅退出"唯一的验收方式。

## 四、配置热加载：改点表不重启

```csharp
public sealed class Poller(IOptionsMonitor<GatewayOptions> opts)
{
    // 每次读 CurrentValue，不要在构造函数里存一份快照
    private GatewayOptions O => opts.CurrentValue;
}
```

**坑**：`IOptionsMonitor` 的变更通知**可能触发多次**（编辑器保存时先清空再写入，会触发两次文件事件）。所以变更回调里要**去抖**，并且**校验后再生效**——一个写坏的 JSON 不能让正在跑的采集停摆。

```csharp
opts.OnChange(Debounce(TimeSpan.FromSeconds(1), next =>
{
    if (!Validate(next, out var why)) { log.Warning("新配置被拒绝：{Why}", why); return; }
    Apply(next);
}));
```

**"配置校验失败时保留旧配置"** 这个行为要写进文档，也是面试可讲的点。

## 五、日志：结构化 + 有上限

```csharp
Log.Logger = new LoggerConfiguration()
    .MinimumLevel.Information()
    .MinimumLevel.Override("Microsoft", LogEventLevel.Warning)
    .WriteTo.Console()
    .WriteTo.File("logs/gw-.log",
        rollingInterval: RollingInterval.Day,
        fileSizeLimitBytes: 20 * 1024 * 1024,
        retainedFileCountLimit: 14,          // 两周
        rollOnFileSizeLimit: true)
    .CreateLogger();
```

**`retainedFileCountLimit` 不设 = 迟早把 SD 卡写满。** 这是嵌入式部署最常见的事故之一，而且发生在你交付三个月之后。

**结构化的意义**：

```csharp
// 不要这样
log.Information($"设备 {id} 读取失败，耗时 {ms}ms");
// 要这样——字段可被检索和聚合
log.Information("设备读取失败 {DeviceId} {ElapsedMs} {ErrorCode}", id, ms, code);
```

**日志分级的现场原则**：`Information` 记状态**变化**（上线、下线、配置变更），不记每次成功采集——1 秒周期的采集打 Info，一天就是 8 万行噪音。

## 六、时间戳：边缘时间还是平台时间（面试常问）

**两个都要，双写。**

| | 边缘时间 | 平台接收时间 |
|---|---|---|
| 含义 | 数据**真实发生**的时刻 | 数据**到达**的时刻 |
| 用途 | 分析、趋势、和生产事件对齐 | 排查延迟、审计 |
| 问题 | 设备时钟可能不准/漂移 | 断网补传时完全失真 |

**为什么补传让平台时间失效**：断网 1 小时后补传，2000 条数据在 5 秒内涌入平台。按平台时间存，这一小时的数据全挤在 5 秒里——曲线彻底废掉。**所以时序库的主时间戳必须是边缘时间。**

**设备时钟不准怎么办**：

1. 网关侧用 NTP 对时（树莓派默认就有 `systemd-timesyncd`）
2. 由**网关**给数据打时间戳，而不是信任每台仪表自己的时钟——大多数 Modbus 仪表压根没有时钟
3. 上报时同时带 `ts`（边缘）和网关的时钟同步状态；平台侧记录 `received_at`
4. 若边缘时间与平台时间偏差超过阈值（比如 5 分钟），打标记但**不要改写数据**

## 七、72 小时连续运行

M2 闸门的硬指标。跑之前先接上观测：

```bash
dotnet-counters monitor -p <pid> --counters System.Runtime
```

**要盯的三条曲线**：

- **工作集内存**：应该锯齿状波动但**基线平稳**。基线持续抬升 = 泄漏。
- **Gen2 回收次数**：稳步增长正常，加速增长说明有东西在往老年代堆。
- **积压条数**：应该贴着 0，偶尔尖峰后迅速回落。

**最常见的三个泄漏源**：

1. 事件订阅没退订（`+=` 了没 `-=`），对象被事件源一直持有
2. `HttpClient` / `SerialPort` 没 `Dispose`
3. 无界的内存集合——统计、缓存、日志缓冲，任何一个 `List<T>` 只加不删
